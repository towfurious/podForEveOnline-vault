# Guide — App Store Launch Readiness

## Goal
Track everything PodForEve needs before a real Google Play / Apple App Store launch, beyond the app's core feature set (which is done and working — 4 screens, OAuth2 login, completion notifications, all committed and tested). Built 2026-07-15 from a full audit of the vault, the codebase, and current external store/CCP requirements. This is a **living tracker** — update the Status column as items get picked up, don't let it go stale.

## How to read this
Three tiers:
- **P0** — blocks store submission or is a hard compliance requirement. Nothing here should be skipped.
- **P1** — strongly recommended before a real public launch; not a hard blocker, but a real risk or quality gap.
- **P2** — legitimate backlog; fine to ship without.

Each row notes whether Claude Code can implement it directly, or whether it needs **your own action** first — an account, a credential, a hosting or wording choice only you can make.

## P2 — backlog, fine to ship without

- **iOS login doesn't use `ASWebAuthenticationSession`, contrary to [[ADR-008 - OAuth2 PKCE via System Browser]]'s own documented decision** — found 2026-07-24 while fixing the Android equivalent issue below. `UrlLauncher.ios.kt` actually uses plain `UIApplication.openURL` (full Safari hand-off), not an in-app auth session. Two consequences once iOS work resumes: (1) it should be switched to the documented API for consistency and a better dismiss/cancel UX, and (2) iOS almost certainly has the same session-cookie-reuse-after-logout exposure Android had — Safari shares cookies the same way Chrome Custom Tabs do — fixable via `ASWebAuthenticationSession.prefersEphemeralWebBrowserSession` once (1) is done. Deliberately not fixed now — iOS work is sequenced after the Android launch per the user's 2026-07-22 call.
- **Android login session-cookie reuse after logout — done (2026-07-24)** — ephemeral Custom Tabs (`setEphemeralBrowsingEnabled`), gated on `isEphemeralBrowsingSupported()` with a device-verified graceful fallback. See [[ADR-008 - OAuth2 PKCE via System Browser]] addendum.
- **AGP 9 → 10 KMP-plugin migration** — [[ADR-012 - Stack Upgrade Kotlin 2.4 CMP 1.11 AGP 9]]'s bypass flags (`android.builtInKotlin=false`, `android.newDsl=false`) will be removed in AGP 10.0, but no firm deadline is known yet.
- **Localization / i18n** — the app is English-only today (zero string externalization, confirmed by grep); reasonable to stay that way for MVP given EVE's playerbase skews English-dominant. Revisit if there's real demand later.
- **Accessibility polish** — `Modifier.semantics` on custom composables (progress bars, status badges). The small existing icon/image surface area is already fully covered (`contentDescription` set correctly everywhere it appears today).
- **`CharacterOwnerHash` migration** — best practice for handling character-ownership transfers correctly (a character can be sold to a new owner; `characterId` alone would then silently point to different real-world data). Confirmed the app uses raw `characterId` as the identity key everywhere today (13 files). Real but low-frequency edge case; the fix is invasive (auth + all four repositories + DB schema) relative to how often it'd actually bite a given user.
- **Remaining [[ADR-015 - Unified Completion Notifications]] deferred items** — `BGAppRefreshTask`/`WorkManager` background rescheduling, tap-to-deep-link, in-app per-category notification settings toggle.
- **Monetization** — not currently planned. CCP's Developer License Agreement permits ISK-based charges, voluntary (non-gating) donations, and ad-network revenue, but **real-money IAP or subscriptions that gate access require separate written CCP authorization**. If a paid tier is ever considered, that conversation with CCP needs to happen first. **Decided 2026-07-17**: lean toward voluntary donations as the only monetization worth pursuing pre-launch — ads were considered and set aside (real complexity: SDK integration, the tracking/privacy-disclosure obligations that come with it, likely poor revenue given how niche this app's audience is) and so was the classic "pay $1 to remove ads" pattern (that's a real-money IAP gating a feature — the ad-free experience — so it falls under the same CCP-authorization requirement as a paywall, not something to route around casually).
- **Donations: US compliance landscape** — researched 2026-07-17 following the monetization decision above. Two separate concerns, not one:
  - *Tax*: PodForEve isn't a registered 501(c)(3), so "donations" are legally just income to whoever receives them, not tax-deductible charitable gifts for the donor — worth phrasing as "support the developer," not "donate," to avoid implying a tax deduction that doesn't exist. Confirmed the recipient side too: this is ordinary taxable income, not a tax-free personal gift under IRS gift rules — a gift requires no connection to a product/service received in return, and support money tied to an app people actually use doesn't qualify, same treatment the IRS already applies to Patreon/Ko-fi/Twitch creator payments. 1099-K threshold reverted to **$20,000 and 200+ transactions** for 2025/2026 (the lower $600 threshold from earlier legislation was rolled back by the "One Big Beautiful Bill") — but that threshold only controls when a payment processor must *file the form*; the underlying income is taxable from the first dollar regardless, form or no form. Money-transmission licensing isn't the recipient's concern as long as an established, licensed processor (Stripe, PayPal, GitHub, etc.) is doing the actual money movement.
  - *Store policy* (this is the part that actually constrains implementation): Apple's App Review Guideline 3.2.1(vii) allows voluntary donations, but as of the post-Epic-v.-Apple external-payment-link changes, **external donation links are explicitly excluded for the "Games" category** — only reader/e-commerce categories get that exemption. Unverified whether the App Store would classify a game-companion utility (no gameplay, just character data) as "Games" or not — needs checking directly against App Store Connect's category picker before relying on an external link (Ko-fi, GitHub Sponsors) working on iOS. Fallback that works regardless of category: Apple explicitly sanctions an in-app "tip" using their own IAP/StoreKit, just with their normal commission. Google Play's current stance on external donation links wasn't confirmed with the same confidence — historically more permissive than Apple, but flagged here as unverified rather than assumed.
  - Leaning toward an external link (GitHub Sponsors or Ko-fi, opened in the browser, not embedded checkout) as the starting point given the code is already on GitHub — contingent on resolving the Games-category question above.
- **`androidx.security.crypto`'s entire API is deprecated by Google, but a stable `1.1.0` release does exist** (correcting an earlier note from earlier the same day — the initial "no stable version was ever released" claim was wrong, caught when the user asked to double-check). Bumped `1.1.0-alpha06` → `1.1.0` 2026-07-17: confirmed zero breaking changes in the official release notes, `EncryptedSharedPreferences`/`EncryptedFile` still present and functional, just annotated `@Deprecated` in favor of "direct Android Keystore use" (no concrete replacement class named yet). Device-verified: existing encrypted refresh token (written by the old alpha06-era library) still decrypts correctly and drives a full auto-login under 1.1.0. A future migration to Jetpack DataStore + Tink remains a real thing to plan for eventually, but isn't urgent — this is a stable, supported release for now.
- **iOS 26 Liquid Glass** — checked 2026-07-17 per user request ("didn't libraries used to block this — check if they still do"). They don't, and never will on their own: this isn't a library-version gap, it's architectural. Per JetBrains' own doc (kotlinlang.org/docs/multiplatform/ios-liquid-glass.html, last modified 2026-06-10): Liquid Glass is rendered *by the system* through native `TabView`/`NavigationStack`/toolbar — Compose Multiplatform draws its own pixels via Skia and never touches that native chrome, so no CMP/Haze/dependency bump can unlock it. The only real path is handing tab-bar + navigation-stack chrome to a native SwiftUI shell while Compose keeps rendering screen *content* — a genuine architectural migration (route title metadata, navigation-interception callbacks between Kotlin and Swift, a standalone per-screen renderer, hiding Compose's own nav chrome), requiring Xcode 26 + iOS 26 SDK. JetBrains' tutorial targets their own Navigation 3 library; this app uses [[ADR-003 - Voyager and Bottom Navigation|Voyager]], so the interception code would need to be written fresh against Voyager's back-stack APIs, not copy-pasted. A much lighter option exists if only the *look* matters, not real system integration: third-party visual-approximation libraries (e.g. `NadeemIqbal/liquid-glass`, `Kashif-E/KMPLiquidGlass`) paint blur/shader effects that mimic Liquid Glass without native chrome — checked whether Haze 2.0's new pluggable `VisualEffect` architecture (already flagged as a P2 alpha-only bump above) was built for this specifically; its own release notes make no mention of Liquid Glass at all, so it's a general-purpose extension point, not a ready answer either way.
- **Back button from any bottom-nav tab exits straight to the launcher** instead of returning to the Dashboard tab — found 2026-07-16 while device-verifying the targetSdk 36 bump, confirmed via an A/B test (identical at targetSdk 35, so pre-existing, not a regression from that change). Likely a Voyager `TabNavigator` characteristic — each tab may be its own root with no shared back-stack. Minor UX polish, not launch-blocking; worth a deliberate decision on whether tabs should share a back-stack (so back always lands on Dashboard) before treating this as intentional.
